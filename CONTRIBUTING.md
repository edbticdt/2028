# Contributing to the EDBT/ICDT 2028 website

The site is published at <https://edbticdt.github.io/2028/>. It is built from
the files in this repository by [Eleventy](https://www.11ty.dev/), and
published automatically when a change is merged into `main`.

There are two ways to contribute:

- **Editing content** (most organisers): change text, dates, committees or
  lists directly on github.com. You need nothing installed.
- **Working on the site itself** (maintainers): change the layout, the styles
  or the build, on your own computer.

> The site is moving to Eleventy. Until that is finished, some files named
> below don't exist yet, the build check on pull requests and the broken-link
> check aren't in place, and the published site is still the old placeholder
> page.

## Where things are

| What you want to change | Where it is |
| - | - |
| Year, dates, city, edition numbers | `src/_data/site.yaml` |
| The text of a page | the page's Markdown file in `src/` |
| Committees, important dates, accepted papers | the YAML files in `src/_data/` |
| Images and logos | `src/images/` |
| PDFs (calls, forms, sponsorship) | `src/resources/` |
| The menu | `src/_data/menu.yaml` |
| Layout and styles (maintainers) | `src/_includes/` and `src/css/` |

Never edit `_site/`: it is generated by the build and not kept in the
repository.

## Editing content on github.com

1. Open the file on github.com and click the pencil icon ("Edit this file").
2. Make the change. Markdown pages use plain text with `#` for headings,
   `**bold**`, and `[link text](https://example.org)` for links. YAML files
   are lists of `name: value` lines: keep the indentation exactly as it is,
   since it carries meaning.
3. Click **Commit changes...**. Write a short message saying what changed,
   such as `content: add the ICDT program committee`.
4. Choose **Create a new branch for this commit and start a pull request**,
   then **Propose changes**, then **Create pull request**.
5. GitHub builds the site for the pull request. If the build fails (a red
   cross), open the details: the message names the file and the problem, often
   a broken link or a YAML indentation error.
6. A maintainer reviews and merges it. The site updates a few minutes later.

Please don't commit straight to `main`, even if GitHub lets you: a pull
request lets the build catch mistakes before they go live.

### Links between pages

Link to another page of this site with a relative path, such as
`[Venue](venue/)`. Never start the link with `/`: the site lives under
`/2028/`, and `/venue/` would point to the EDBT/ICDT organisation's own
site instead.

## Working on the site locally

You need [Node](https://nodejs.org/) 26. With
[fnm](https://github.com/Schniz/fnm), from the repository root:

```sh
fnm use        # selects the Node version in .nvmrc
npm ci         # installs the exact package versions from package-lock.json
npm start      # builds the site and serves a live preview
```

`npm start` prints a local address. The preview reloads on every save.

Other commands:

| Command | What it does |
| - | - |
| `npm run build` | Builds the site once into `_site/` |
| `npm run build:pages` | Builds with the `/2028/` prefix, as the deploy does |

Everything stays inside the repository: packages go into `node_modules/` and
npm's download cache into `.npm-cache/`, both ignored by git. The project's
`.npmrc` pins exact versions and blocks package install scripts. Never
install with `-g` or run npm with `sudo`.

### Adding or upgrading a package

Keep packages to a minimum: every one is something the next edition's team
has to maintain. Agree any new package with the maintainers first. Then
`npm install --save-dev <package>@<version>`, and commit `package.json` and
`package-lock.json` together, in a commit of their own.

## Commit messages

```
<type>(<scope>): <subject>
```

- **type**: `content` for text and data, `fix`, `feat`, `docs`, `style`,
  `build`, `ci`, `chore`
- **scope**: optional, the part of the site, such as `program` or `venue`
- **subject**: imperative and lowercase, with no final period, such as
  `content(venue): add the travel directions`

Keep each commit to one topic.

## Handing over to the next edition

The site is built so that the next edition can reuse it:

1. Copy the repository for the new edition.
2. Update `src/_data/site.yaml`.
3. Replace the content pages and the data files in `src/_data/`.
4. Replace the logos in `src/images/`.
5. Remove the menu entries for pages the new edition doesn't have yet. The
   build fails on a menu entry or link to a page that doesn't exist, so
   nothing goes live as a broken link.

The layout and the build need no change.
